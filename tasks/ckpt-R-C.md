Apply: backs up `/opt/telcoin/telcoin-network` to `telcoin-network.bak.<ts>`, stops, installs, starts, verifies. Warns "Binary hash did not change after build." + `Proceed anyway with the existing (unchanged) binary?`; hash change between prepare and apply: `Proceed anyway?`.
- Docker path: pull new image (`Proceed with the pull?`), edit the image ref in the launch file (wrapper `/opt/telcoin/start-telcoin.sh`, else the unit), backup `<file>.bak.<ts>`, `daemon-reload`, restart, verify the running container is on the pulled image.
- Validator gate: before stopping, if on-chain status is registered validator (1-4) OR unknown: banner "VALIDATOR DOWNTIME WARNING" ("Stopping a validator during its committee window means missed consensus rounds and lost block rewards") and prompt `Type CONFIRM to proceed with the validator restart: `. Skipped only when registry says Undefined/Exited/Retired/no NFT. JSON: `--apply` needs `--yes` else error "validator apply requires explicit confirmation (--yes)".
- Verify [verify_health_after_restart]: polls every 3 s up to `VERIFY_TIMEOUT_SECONDS` (default 45; `TN_UPDATE_VERIFY_TIMEOUT` digits only, "when every peer restarts at once... quorum takes longer to re-form than a single-node restart, and the default window would trigger a spurious auto-rollback") for service active AND `tn_latestConsensusHeader` returning a `"result"`. Failure: "Service did not become healthy within 45s". Also identity checks (running binary hash / container image must match what was prepared).
- Rollback: interactive failure => "Post-update verification failed." then `Roll back to previous binary?` / `Roll back to previous image (<old>)?` (y => restore backup, restart, re-verify: "Rolled back to <old>"; n => "Leaving node on new image. Pending state cleared."). JSON apply failure auto-rolls back: done `{"event":"done","ok":false,"phase":"apply","rolled_back":true,"msg":"health check failed; rolled back to previous binary"}` (or `previous image`); if restore fails `rolled_back:false` + "service left stopped -- restore <backup> to <file> manually". If the backup restore itself fails interactively: "Node left STOPPED. Recover manually: cp -p <backup> <file> && systemctl daemon-reload && systemctl start telcoin".
- `--json` actions (all need root, emit to fd3): `--check` (no event; one object `{"install_method","current_ref","latest_ref","update_available","pending"}`), `--prepare --ref <ref>` (error "no ref supplied" if missing; done `{"phase":"prepare","new_ref","new_version"}` or `{"phase":"prepare","new_image"}`), `--apply [--yes]` (done `phase:apply`), `--discard` (done `phase:discard`, "pending update cleared" / "no pending update to discard"). Unknown action: "unknown or missing --json action". Source JSON `--ref` = git branch/tag/commit; docker `--ref` = bare tag (composed onto the current registry path) or full image ref.
- "latest" per method [update-node.sh]: source = newest git tag by `--sort=-creatordate` after `git fetch --tags --force`, filtered to names containing the network suffix (`-adiri` for testnet, `-telcoin` mainnet, devnet none = newest tag of any kind); `update_available` when HEAD is not exactly on that tag. Interactive source picker = same `pick_source_version` as setup (default = latest tag for testnet/mainnet, `main` for devnet). Docker = highest version among the last 15 registry tags (`fetch_docker_tags`), menu newest first with `<-- latest` / `<-- current`, plus `Custom tag` and `Cancel`; unreachable registry => "Could not reach registry (or no parseable tags returned)." + manual tag prompt.

## 7. install-caddy.sh  [install-caddy.sh; README "Public RPC endpoint"]
- `readonly SCRIPT_VERSION="1.3.0"`. Root: YES (`check_root` in enable/disable phases and the interactive menu). Debian/Ubuntu only for the package install (`apt-get`, Cloudsmith repo `dl.cloudsmith.io/public/caddy/stable`, keyring `/usr/share/keyrings/caddy-stable-archive-keyring.gpg`). Needs `python3` to edit node-info.yaml ("python3 not found -- cannot edit node-info.yaml. The endpoint works but won't be advertised on-network").
- Purpose [header]: "External (public) access via Caddy: dashboard + RPC"; one managed `/etc/caddy/Caddyfile` with two fenced vhosts: `# >>> tn-dashboard >>>` (-> `127.0.0.1:8080`, basic_auth, READ-ONLY via header `X-TN-Dashboard-Public`) and `# >>> tn-rpc >>>` (`https://<d>/` -> `127.0.0.1:${RPC_PORT}`, `wss://<d>/` -> `127.0.0.1:${WS_PORT}`; ports read from .node-meta, default 8545/8546). RPC vhost = pure reverse proxy + CORS (`Access-Control-Allow-Origin "*"`, OPTIONS answered at edge); NO method filtering in Caddy (what is exposed is whatever reth's http/ws namespaces allow).
- Usage [header]:
  - Interactive: `sudo bash install-caddy.sh` -> menu `[1] Dashboard (Node Manager UI) -- public HTTPS access with a login`, `[2] Public RPC endpoint -- https/wss JSON-RPC, advertised on-network`, `[3] Show status`, `[q] Quit` (`Choose [1/2/3/q]:`); RPC sub-menu `[e] enable / re-configure`, `[d] disable`, `[b] back`.
  - Human non-interactive (`--phase=` without `--json`): `status | check-dns | enable | disable | rpc-status | rpc-check-dns | rpc-enable | rpc-disable`. Quote: `--phase=rpc-check-dns --rpc-domain <d>   (exit 0 = DNS reaches this host)`; `--phase=rpc-enable --rpc-domain <d> [--move-dashboard-to <host>]`. Unknown phase => "unknown --phase '<x>' (status|check-dns|enable|disable|rpc-status|rpc-check-dns|rpc-enable|rpc-disable)". 
  - JSON: `--json --phase=<same list>`.
- Flags: `--json`, `--phase <p>`/`--phase=<p>`, `--domain` (dashboard), `--username` (dashboard; 2-32 chars `[A-Za-z0-9._-]`), `--rpc-domain`, `--move-dashboard-to <host>` (rpc-enable only), `--public-ip <ip>` (also env `TN_CADDY_PUBLIC_IP`; the INBOUND public IP). Unknown flags are silently ignored (`*) shift`). Env: `TN_CADDY_PASSWORD` (dashboard password, min 8 chars: "password too short (minimum 8 characters)"; never argv), `TN_CADDY_PUBLIC_IP`, `TN_ASSUME_YES` (inherited from common.sh `confirm`).
- JSON events: `status`/`rpc-status`/`check-dns`/`rpc-check-dns` emit ONE bare object, not events: status `{"installed","running","enabled","domain","username"}`; rpc-status `{"installed":b,"running":b,"enabled":b,"domain":"..","advertised_http":"..","advertised_ws":"..","ws_listening":b}`; dns `{"domain","public_ip","resolved_ip","propagated":bool,"egress_ip","local_ips":[..],"note":".."}` (setup-node.sh keys on `"propagated": true`). enable/disable/rpc-enable/rpc-disable emit `step` events and `{"event":"done","ok":true,"domain":..,"msg":"public RPC endpoint enabled -- certificate issues on first request"}` (rpc-disable: "public RPC endpoint disabled"). Failure with no done: json_on_exit "exited early (rc=...)". Unknown JSON phase: `{"event":"done","ok":false,"msg":"unknown or missing --phase (...)"}`.
- `rpc-enable` sequence (`do_rpc_enable`): validate domain (`caddy_validate_domain`) -> same-host clash check vs dashboard (or `--move-dashboard-to`) -> `caddy_assert_ports_free` (80/443 not held by another web server) -> `caddy_assert_not_foreign` (existing hand-made Caddyfile) -> install Caddy if missing -> write Caddyfile via validate/backup/atomic swap -> `ufw allow 80/tcp` + `443/tcp` if ufw active -> reload Caddy -> WebSocket preflight -> advertise in node-info.yaml and restart node (brick-guarded) -> `caddy_ws_verify` (5 x 2 s: "reth WebSocket listening on port 8546 -- wss://<d>/ is served.").
- What it edits: (a) `/etc/caddy/Caddyfile` (backup `/etc/caddy/Caddyfile.bak.<YYYYmmdd_HHMMSS>`, `cp -p`, never deleted; a foreign Caddyfile is first saved as `/etc/caddy/Caddyfile.tn-orig`); (b) `<DATA_DIR>/node-info.yaml` -- sets `rpc` (http `https://<d>/`, ws `wss://<d>/`) on EVERY entry of `workers:` (and legacy `worker:` map) via python3 stdlib; backup `node-info.yaml.tn-bak` (removed if unchanged/after success); (c) the node launch file, ONLY if reth WS is not already listening and the launch lacks `--ws`: appends `--ws --ws.addr 127.0.0.1 --ws.port <WS_PORT>` to the `--http` line of `/opt/telcoin/start-telcoin.sh` (or the unit for legacy docker), backup `<file>.tn-bak`; (d) restarts the node once. Setup-node already bakes `--ws --ws.addr 127.0.0.1` so for new installs (c) is normally a no-op.
- Brick guard [header]: after restart checks "up to 30 times, about 2 s apart (~60 s), for RPC to answer. Only a unit that reaches systemd's `failed` state inside that window ... gets node-info.yaml and the launch edit rolled back and the node restarted on the previous config. A node still auto-restarting (RestartSec) or replaying its DB when the window ends is NOT rolled back -- the change is kept, with a warning." Warning text: "<svc> is still starting (DB replay?) and RPC has not answered yet. The change is kept and will take effect once the node is up. Backup(s): ..."
- WS fallbacks (https-only advertisement + warning): port held by another process ("The reth WebSocket port 8546 is held by '<proc>', not the node ... Advertising https:// only (no wss://)"); no node service; launch file missing; `--http` line continues onto next line / is a comment (edit refused, tells operator to add the flags by hand and re-run). 
- DNS check (`rpc-check-dns`/`check-dns`): human output `Domain:`, `Resolves to:`, `Effective public IP: <ip>   (egress: <ip>)`, `Bound local IP(s):`; OK when A record equals the effective public IP (the `--public-ip` override, else ipify egress IP) or any bound local IP; otherwise the note: "<d> resolves to <ip>, which is neither this host's effective public IP (...) nor a bound local IP (...). Note that <egress> is this box's EGRESS (outbound) IP, which can differ from the INBOUND IP where ACME reaches you on a multi-IP or NAT host -- ... supply it with --public-ip <ip> (or set TN_CADDY_PUBLIC_IP) and re-check." Interactive gate: `Press Enter to check DNS propagation once the record is set...` then `[r]echeck / [c]ontinue anyway / [a]bort:` ("Continuing despite DNS mismatch -- cert issuance may fail."). Interactive public-IP prompt `Server's inbound public IP [<default>]: `.
- Let's Encrypt rate limits: header/README only warn ("if DNS isn't pointing here (and ports 80/443 reachable), ACME fails and Let's Encrypt rate-limits you"; README: "issuance fails and retries get rate-limited"). There is no automatic rate-limit detection or staging-CA fallback in the script. After enable: "The TLS certificate is issued on the first request -- give it a few seconds."
- Apache/Nginx conflict: non-interactive => die "port 80 is in use by '<proc>' -- Caddy needs it and cannot share with another web server. Stop/remove it first (Apache: 'sudo systemctl disable --now apache2'), or run 'sudo bash install-caddy.sh' on the server to be guided through removing it." Interactive (`resolve_port_conflicts`): "Apache (apache2) is using a port Caddy needs (80/443) -- they cannot run together." with `[s] stop & disable apache2 / [p] stop, disable & remove (purge) / [q] quit` (nginx/lighttpd: only `[s]`/`[q]`). Unknown holder: "ports 80/443 are in use by '<p>', which I do not know how to stop safely."
- Foreign Caddyfile: JSON/non-interactive refuses: "an existing Caddy configuration at /etc/caddy/Caddyfile was not created by the Node Manager -- refusing to overwrite it. Run 'sudo bash install-caddy.sh' on the server to review and confirm, or back up and remove the existing config first." Interactive: `[o] back up and overwrite / [q] quit`.
- Hostname clash (dashboard vs RPC): "<d> already serves the Node Manager dashboard -- the dashboard and the public RPC endpoint need DIFFERENT hostnames. The node's public name (e.g. nodeN.adiri.telcoin.network) should carry the RPC endpoint, with the dashboard on another hostname (e.g. dashboard.<d>). Nothing was changed. To move the dashboard (same login) and enable RPC in one step, first create the DNS A record for dashboard.<d> pointing at this server ... then run: sudo bash <dir>/install-caddy.sh --phase=rpc-enable --rpc-domain <d> --move-dashboard-to dashboard.<d>". `--move-dashboard-to` must differ from `--rpc-domain` and is ignored (info line) if the dashboard is not on the RPC host. Interactive offer: `Move the dashboard to dashboard.<d> and use <d> for RPC? [y/N]: `.
- Interactive RPC flow text: "Exposes this node's JSON-RPC publicly at https://<rpc-domain>/ (+ wss://) behind Caddy with automatic TLS. reth stays loopback-only ... Enabling ALSO advertises the endpoint in node-info.yaml (so peers discover it) and RESTARTS the node." prompts `Public RPC domain (e.g. node1.adiri.telcoin.network): `, DNS A record reminder, "If this host is behind NAT, port-forward 443/tcp (required) and 80/tcp (recommended)." then `Proceed? [y/N]: `.
- `rpc-disable`: un-advertises (clears `rpc` in node-info.yaml, restarts node), removes the `tn-rpc` block, keeps dashboard; when no vhost remains tears Caddy config down and closes 80/443 in ufw (`caddy_close_ports`). `--ws` flag stays in launch file. Interactive: "Disabling un-advertises the endpoint (node-info.yaml) and restarts the node." + `Proceed? [y/N]:`.
- Verification commands (README "Check it"): `sudo bash ~/telcoin-node-scripts/check-node.sh` (ends `public RPC: OK` / `public RPC: WARN -- <reasons>`; private node: `public RPC: not configured (private node)`), and `sudo bash ~/telcoin-node-scripts/install-caddy.sh --phase=rpc-status`. README does NOT document a manual `curl https://<d>/ ... eth_chainId` or wss client check; setup-node.sh's final summary prints only the LOCAL `curl ... http://127.0.0.1:8545` eth_chainId. (check-node internally probes `curl --resolve <d>:443:127.0.0.1` eth_blockNumber and a 101 WebSocket upgrade -- the docs writer can adapt those as copy-paste checks.)
